## 第一阶段：知识生成（源码 → 知识）

### 1.1 问题：生成顺序是否影响生成质量

**描述**：仓库级代码文档生成时，文件之间存在依赖关系。如果被依赖文件的文档尚未生成，当前文件生成时会缺少上下文信息，导致文档质量下降。

**已有解决方案参考**：

| 方案 | 来源 | 核心做法 | 不足 |
|------|------|----------|------|
| DAG 拓扑序调度 | RepoAgent (EMNLP 2024) | 按文件间依赖关系构建 DAG，按拓扑序逐文件生成文档，保证被依赖文件先生成 | 仅考虑文件级依赖，粒度粗 |
| 语义影响传播算法 | RepoDoc (2026) | 构建异构知识图谱（函数/类/接口等多种节点），通过语义影响传播算法决定文档生成和更新范围，比纯 DAG 更精细 | 实现复杂度高 |
| 策略-依赖感知的拓扑顺序 | RepoRepair (2026) | 在 DAG 拓扑基础上增加策略优化，更贴合修复场景需求 | 面向修复场景，通用性待验证 |
| 依赖分析 + 按顺序测试 | Scaling TDD (2026) | 分析类间依赖关系，按拓扑序执行测试，避免循环依赖 | 面向测试执行，非文档生成 |

**飞轮当前设计**：采纳拓扑序调度，知识处理顺序 = 依赖拓扑序，先依赖后被依赖（FLYWHEEL-DESIGN.md §2）。

**待解决的问题**：
- 拓扑序的具体实现：文件级还是组件级？pptx 中提到"按目前的结构来看，知识对应的形式为一篇 md 文档"，需确定文档粒度
- 顺序敏感性的验证：换一种顺序结果是否稳定（知识飞轮流程设计.md §9.2）

### 1.2 问题：如何初始化 skill 以快速启动

**描述**：飞轮需要迭代收敛，如果初始 skill 质量差，迭代次数多、成本高。如何让初始迭代次数就比较少？

**已有解决方案参考**：

| 方案 | 来源 | 核心做法 |
|------|------|----------|
| 两轮文档生成 | RepoRepair (2026) | 先生成概要文档再生成细节文档，分阶段提升质量 |
| 多 Agent 协作生成 | DocAgent (2025) | AST 解析 + 依赖图 → 拓扑排序 → 逐组件由多 Agent 协作生成 docstring |
| 领域模型作为骨架 | SSDE (2025) | 预先定义好领域模型（数据结构、接口签名），LLM 只需填充实现逻辑，缩小生成范围 |
| 渐进式编码 | Spec2RTL-Agent (2025) | 先写伪代码，逐步过渡到最终代码（Pseudo → Python → C++ → RTL） |
| Template-driven 约束 | Spec Kit (GitHub) | 通过结构化模板约束 LLM 输出：强制 `[NEEDS CLARIFICATION]` 标记不确定点、checklist 自检、constitutional compliance gates 架构合规门禁，从源头提升初始生成质量 | 模板面向 spec 编写而非知识提炼，需适配飞轮的知识形态 |

**飞轮当前设计**：
- 知识形态为"伪代码 + 为什么这样设计"，保留实现逻辑的"魂"而非代码的"壳"（知识形态定义.md）
- pptx 建议做"简单对比实验"：取一部分代码仓作为用例，测试不同初始 skill 及生成框架的迭代初始代数和下降速度

**与 Spec Kit 的关系**：Spec Kit 的 template-driven 约束机制（uncertainty markers + checklist + constitutional gates）可直接用于飞轮 skill 初始化——在知识生成 skill 中嵌入类似的 checklist 和 `[NEEDS CLARIFICATION]` 机制，迫使 LLM 在知识不完整时标注而非猜测，减少初始迭代次数。

**待解决的问题**：
- 单 agent 直接用一个 skill，还是这一步就使用多 agent 系统？（pptx Slide 4）
- 与其他文档的关系、更新顺序、是否需要其他文档参考

### 1.3 问题：知识生成框架的选择（单 Agent vs 多 Agent）

**描述**：知识生成是用单 agent 直接一个 skill 完成，还是使用多 agent 系统协作？

**已有解决方案参考**：

| 方案 | 来源 | 核心做法 | 优劣 |
|------|------|----------|------|
| 单 Skill 直接生成 | 飞轮基础设计 | 一个 Skill（GLM 5.1）读源码 → 提炼伪代码 + 为什么 + 埋溯源链接 → 知识文档 | 简单，但初始质量可能差 |
| 多 Agent 协作 + Verifier 反向触发 | DocAgent (2025) | 多 Agent 协作生成 docstring，引入 Verifier 角色评估质量，可反向触发更多上下文收集，形成闭环质量保障 | 质量更高，但系统复杂 |
| 异构知识图谱驱动 | RepoDoc (2026) | 以组件（而非单文件）为文档粒度，多语言支持 | 粒度更合理，但实现复杂 |

**飞轮当前设计**：知识生成 Agent 加载"知识生成 skill"按手册干活，skill 是操作手册，agent 是执行者（知识飞轮流程设计.md §3.1）。

**待解决的问题**：
- 多 Agent 系统的编排方式（参考 langgraph 的 StateGraph / create_react_agent）
- Verifier 角色是否引入以及如何实现

### 1.4 问题：生成的知识缺乏验证

**描述**：多数论文停留在"生成即完成"阶段，缺少对生成知识的一致性和正确性的验证机制。

**已有解决方案参考**：

| 方案 | 来源 | 核心做法 | 不足 |
|------|------|----------|------|
| 多 Agent 评估验证 | DocAgent (2025) | Verifier 评估 docstring 质量，可反向触发更多上下文收集 | 验证仅靠 LLM 判断，缺乏形式化或可执行验证手段 |
| 飞轮闭环验证 | 飞轮方案本身 | 知识→代码→对比差异→反馈迭代，用代码还原度验证知识质量 | 需要完整的代码生成和评测环节配合 |
| 多信号打分 | wpKnowledge MVP | 溯源完整性 + 结构质量 + 时效 + 去重 + 可验证性 + LLM 陪审团 + 使用反馈，七信号加权 | 语义一致性验证尚未实现 |
| Cross-artifact 一致性分析 | Spec Kit (GitHub) `/speckit.analyze` | 跨 artifact（spec ↔ plan ↔ tasks）一致性与覆盖度分析，检测歧义、矛盾、缺口 | 分析依赖 LLM 判断，非可执行验证；面向 spec artifact 而非知识文档 |

**飞轮当前设计**：
- 知识文档每段标注对应源码位置（溯源链接），diff 差异时反向映射定位需修改段落（知识飞轮流程设计.md §4）
- wpKnowledge MVP 已实现五信号确定性打分 + 可选 LLM 陪审团 + 门禁机制（FLYWHEEL-DESIGN.md §4）

**与 Spec Kit 的关系**：Spec Kit 的 `/speckit.analyze` 提供了跨 artifact 一致性分析的思路——飞轮可借鉴其对 spec ↔ plan ↔ tasks 的一致性检查模式，实现知识文档 ↔ 源码 ↔ 生成代码之间的三方一致性验证。但 Spec Kit 的分析依赖 LLM 判断，飞轮需要补充客观信号（编译、测试、AST 对比）。

**待解决的问题**：
- 代码-知识语义一致性验证尚未实现（FLYWHEEL-DESIGN.md §11）
- LLM 自评不可作主信号，需客观外部验证（知识飞轮流程设计.md §9.4）

### 1.5 问题：知识无时间维度，不支持增量更新

**描述**：几乎所有论文都未考虑知识的版本管理和增量更新，知识会随代码变更快速过时。

**已有解决方案参考**：

| 方案 | 来源 | 核心做法 | 不足 |
|------|------|----------|------|
| 时间有效性标注 + 废止链 | Temporal Validity in RAG (2025) | 知识条目 = {内容, valid_from, valid_until, superseded_by}，半开区间标注有效窗口，检索时自动过滤已废止条目 | 验证机制仅依靠 LLM 判断时间标注可信度 |
| 双层图结构 + 时间边 | RAG Meets Temporal Graphs (2025) | 双层图结构，知识图谱关系边上附加时间信息，实现时序敏感检索 | 未在代码场景验证 |
| 半衰期公式 | Solving Freshness in RAG (2025) | 为知识新鲜度建模，量化计算知识有效期限 | 仅以时间为维度，未考虑知识稳定性、变更频率等 |
| 版本控制 + 门禁 + 回滚 | 飞轮方案 | 知识变更走版本控制，未过门禁不合并，优化使知识倒退时自动回退 | 实现中文件写入无事务/锁 |

**飞轮当前设计**：
- wpKnowledge MVP 已实现：`stale_after` 时效衰减信号、版本号管理、`history/` 旧版快照、防污染回滚（FLYWHEEL-DESIGN.md §4, §10.5）
- pptx 提出：建库时和增量更新维护时应区分，建库时可参考几乎只有代码，增量更新维护时可参考原有知识库或新增的需求说明

**待解决的问题**：
- 增量更新的触发机制：代码变更 → 影响范围分析 → 知识更新范围
- pptx Slide 3 提出：增量更新维护部分可当作原有基础上迭代的第二轮继续

## 第二阶段：代码生成（知识 → 代码）

### 2.1 问题：如何保证编码的准确性

**描述**：一个固定的 coder，要在只有知识库的信息情况下给出代码，如何缩小生成范围、降低错误率？

**已有解决方案参考**：

| 方案 | 来源 | 核心做法 | 不足 |
|------|------|----------|------|
| 渐进式编码 | Spec2RTL-Agent (2025) | Pseudo → Python → C++ → RTL，逐层精化，每步缩小 LLM 生成范围 | 无增量更新，验证仅靠 LLM 判断 |
| 领域模型作为骨架 | SSDE (2025) | 预先定义好领域模型（数据结构、接口签名等），LLM 只需填充实现逻辑 | 领域模型是人工创建的，自动化程度不足 |
| Code to Contract 逆向 | SDD (2025) | 先分析现有代码提取规约，再用规约指导后续代码生成，保证一致性 | 细节待深入了解 |
| 视图分离 + Governance Gates | Spec Growth Engine (2025) | 不同角色关注不同视图，通过分级治理门禁管控变更 | 纯理论框架，缺乏实际实现 |
| Spec-driven 分层约束 | OpenSpec (Fission-AI) | proposal（意图+范围）→ specs（需求+场景，可测试）→ design（技术方案）→ tasks（分步实施清单），Coder 按 task 逐步生成，每步生成范围被严格约束；`/opsx:apply` 按 tasks.md 逐 item 实现，`/opsx:verify` 校验实现与 spec 一致性 | spec 本身的质量依赖人工/AI 编写，不解决 spec 怎么写全的问题；非闭环，无迭代反馈机制 |
| Constitution + Phase Gates | Spec Kit (GitHub) | 9 条宪法条款（Library-First、CLI Interface、Test-First、Simplicity、Anti-Abstraction、Integration-First Testing 等）作为架构约束，实施前必须通过 Phase -1 Pre-Implementation Gates（简洁性门禁、反抽象门禁、集成优先门禁），未通过需在 Complexity Tracking 中记录理由 | 宪法条款面向通用软件开发，需适配飞轮的"知识→代码"场景 |

**飞轮当前设计**：
- Coder Agent 只负责检索知识 + 写代码，不负责验证，不承担迭代逻辑（知识飞轮流程设计.md §3.1）
- 知识形态为"伪代码 + 为什么"，伪代码保留边界处理、数据结构、调用关系等逻辑细节

**与 OpenSpec 的关系**：OpenSpec 的 spec-driven 分层约束与飞轮的"知识约束编码"思路一致——都是通过文档约束缩小 Coder 生成范围。区别在于飞轮的约束来自知识文档（从源码提炼），OpenSpec 的约束来自规格文档（需求+场景+技术方案+实施步骤）。OpenSpec 的 tasks 分步实施机制可直接参考用于飞轮 Coder 的"按 task 逐步生成"实现，`/opsx:verify` 的 spec 一致性校验思路可参考用于飞轮的门禁验证。

**与 Spec Kit 的关系**：Spec Kit 的 Constitution + Phase Gates 机制提供了一种"架构级约束 Coder 行为"的思路——飞轮可在知识文档中嵌入类似的架构约束条款（如"必须保留原有接口签名""禁止引入新依赖"等），Coder 生成前先过门禁检查。Spec Kit 的 9 条宪法中 Test-First（先写测试再写实现）和 Simplicity（≤3 项目、禁止 future-proofing）对飞轮 Coder 的约束设计有直接参考价值。

**待解决的问题**：
- Coder 的上下文怎么构建？pptx 提出"三层（结构 + 知识 + 引用），拓扑序检索"
- 是否有现成实现可参考（OpenSpec 的 artifact 依赖图 + context-injection 机制可参考）
知识库的卡片或者具体代码作为prompt

### 2.2 问题：Coder 上下文构建

**描述**：Coder 需要足够的上下文才能准确生成代码，但上下文过多会超出 token 限制或引入噪声。

**已有解决方案参考**：

| 方案 | 来源 | 核心做法 |
|------|------|----------|
| 三层上下文 | pptx Slide 10 | 结构（代码仓库结构）+ 知识（知识库文档）+ 引用（依赖的知识），拓扑序检索 |
| 多路召回 + 质量重排 | wpKnowledge MVP | BM25 检索 + 质量重排 + 证据充分性规则（weak 不能单独支撑结论），检索可审计 |
| 链式检索 | wpKnowledge 研究 | 沿知识依赖链逐步检索，保证上下文完整性 |
| Artifact 依赖图 + context-injection | OpenSpec (Fission-AI) | proposal → specs → design → tasks 构成 artifact 依赖图，Coder 按 DAG 拓扑序加载依赖 artifact 作为上下文；context-injection 机制将相关 spec/design 片段注入 Coder prompt | 依赖图是 artifact 级而非代码级，粒度较粗；不处理知识库检索的质量重排 |
| `get_info` 按需检索工具函数 | CoverUp (FSE 2025) | LLM 可主动调用 `get_info("symbol")` 请求额外代码上下文（函数/类/模块/变量定义），沿 import 链追踪定义；对类/模块用 `...` 省略非关键部分避免响应过长 | 面向代码符号检索，不涉及知识库文档；需要 LLM 具备 tool-calling 能力 |

**飞轮当前设计**：
- wpKnowledge MVP 已实现 BM25 检索 + 质量重排（FLYWHEEL-DESIGN.md §10.6）
- 检索公式：`relevance = normalized_bm25 * (1 - quality_weight) + score/100 * quality_weight`

**与 OpenSpec 的关系**：OpenSpec 的 artifact 依赖图（proposal→specs→design→tasks）是一种上下文组织方式，与飞轮的"三层上下文（结构+知识+引用）"思路对应——OpenSpec 的 specs 对应飞轮的"知识"，design 对应"引用"，tasks 对应"结构"。飞轮可参考 OpenSpec 的 context-injection 机制实现拓扑序上下文注入，但需补充知识库检索的质量重排（OpenSpec 不覆盖）。

**与 CoverUp 的关系**：CoverUp 的 `get_info` 工具函数提供了一种"LLM 按需拉取上下文"的思路——不同于飞轮的"预先检索+注入"推送模式，CoverUp 让 LLM 自主决定需要哪些额外上下文。飞轮 Coder 可借鉴此模式：在知识库检索结果不完整时，允许 Coder 主动请求更多上下文（如调用知识库的链式检索接口），而非被动接受一次性注入。CoverUp 对类/模块用 `...` 省略非关键部分的做法也可参考用于飞轮的上下文压缩。

**待解决的问题**：
- 拓扑序检索的具体实现：如何沿依赖链组织上下文（可参考 OpenSpec 的 artifact 依赖图 + context-injection）
- 知识完整性问题：关联到模型能否有足够的知识去实现，外部知识可能存在省略、残缺
是否自动压缩

## 第三阶段：评测 / 门禁

### 3.1 问题：如何保证测试用例的质量、准确性和全面性

**描述**：门禁依赖测试用例，但测试用例本身的质量如何保证？

**已有解决方案参考**：

| 方案 | 来源 | 核心做法 | 不足 |
|------|------|----------|------|
| Spec → Test 框架 | Grounding AI Agents in Contracts (2026) | 从规格说明自动生成测试用例，保证测试与需求的可追溯性 | 没有验证 test 本身的质量 |
| 依赖分析 + 按顺序测试 | Scaling TDD (2026) | 分析类间依赖关系，按拓扑序执行测试 | 公共测试是人工预先提供的 |
| Test 分级 Review 机制 | TestGen AI | 对生成的测试用例按重要性/风险分级，不同级别走不同 review 流程 | 纯靠 LLM 确定 test 好坏 |
| 用 debug 确定 test 正确性 | Revisit Self-Debugging (2025) | 通过实际运行和调试验证自生成测试的可靠性，In-Execution 思路从中间状态获取反馈 | 存在信息噪声，实现难度大 |
| 多信号组合门禁 | 飞轮方案 | 编译前置（不过即停）+ UT 为主信号（行为等价）+ AST 相似度辅助（UT 覆盖盲区时启用） | 阈值设定待定 |
| Test-First Imperative | Spec Kit (GitHub) Article III | 宪法强制：先写 unit test → 用户审批 → 确认测试 FAIL（Red phase）→ 才允许写实现代码，non-negotiable | 测试质量仍依赖人工审批，非自动化验证 |
| 覆盖率驱动迭代生成 | CoverUp (FSE 2025) | 迭代式：LLM 生成测试 → 执行 → 覆盖率分析 → 将未覆盖的行/分支明确反馈给 LLM → LLM 修改测试补充覆盖 → 重复直到覆盖率达标。实现 80% 中位行+分支覆盖率（vs CODAMOSA 47%） | 面向覆盖率而非行为正确性，高覆盖率 ≠ 好测试；仅 Python |
| SBST + LLM 混合测试生成 | CODAMOSA (ICSE 2023) | 搜索+LLM 协同：SBST（MOSA 算法）正常进化，当覆盖率停滞（连续 maxStallLen 轮无提升）时，按覆盖率反比概率采样低覆盖函数，用 Codex 生成示例测试用例注入种群，帮助 SBST 逃逸覆盖率高原；uninterpreted statements 支持 Pynguin 无法原生解析的任意 Python 表达式 | 不生成 test oracle（仅覆盖，不检测 bug）；LLM 生成代码的解析率仅 59.3%；纯 LLM 基线（CodexOnly）覆盖率远低于 CODAMOSA，说明 LLM 单独使用效果有限 |

**飞轮当前设计**：
- pptx Slide 17 提出：UT 为主信号（行为等价），AST 相似度辅助（UT 覆盖盲区时启用，验证还原度），编译前置（不过即停）
- 具体每一道门禁阈值：编译以及用例通过率应该是 100%，相似度等可考虑动态调整
- 是 code 错了还是 test 错了：依靠源码跑 test 确定，默认源码正确

**与 Spec Kit 的关系**：Spec Kit 的 Article III Test-First Imperative 与飞轮的"门禁依赖测试"思路高度一致。Spec Kit 强制"先写测试→确认 FAIL→再写实现"的流程，可参考用于飞轮门禁中 UT 的生成顺序——先从知识文档生成 UT，确认 UT 在源码上通过（Red→Green），再用 UT 检验生成代码。但 Spec Kit 依赖人工审批测试，飞轮需要自动化替代方案（源码跑 test 确认）。

**与 CoverUp 的关系**：CoverUp 的覆盖率驱动迭代生成机制直接解决了飞轮"UT 覆盖率要求（覆盖到什么程度算足够）"的问题——不是一次性生成测试，而是迭代补充直到覆盖率达标。飞轮可借鉴此机制用于 UT 生成：从知识文档生成初始 UT → 在源码上运行获取覆盖率 → 将未覆盖部分反馈给 LLM 补充 UT → 重复直到覆盖率达标。但 CoverUp 仅追求覆盖率（覆盖了什么），飞轮还需验证行为正确性（覆盖得对不对），需结合 Spec Kit 的 Red Phase 确认。

**与 CODAMOSA 的关系**：CODAMOSA 提供了一种与 CoverUp 互补的测试生成思路——CoverUp 是"纯 LLM 迭代"，CODAMOSA 是"SBST 搜索 + LLM 提示"协同。CODAMOSA 的核心洞察是：LLM 擅长生成"看起来合理"的测试输入（如版本字符串 `'1.2.2'`），SBST 擅长在已有测试基础上变异探索，两者结合可以逃逸单方法无法突破的覆盖率高原。飞轮可借鉴此混合策略用于 UT 生成：当纯 LLM 生成的 UT 覆盖率停滞时，引入 SBST 变异策略对已有 UT 进行结构化探索，或将 SBST 生成的测试种子与 LLM 生成测试合并。CODAMOSA 的 low-coverage targeting（按覆盖率反比概率采样目标函数）也可参考用于飞轮 UT 生成的优先级排序——优先为覆盖率最低的函数生成测试。

**待解决的问题**：
- UT 由谁编写（从需求描述生成？从标准代码派生？人工维护？）
- UT 覆盖率要求（覆盖到什么程度算"足够"）
- 相似度门限如何确定（80% 的依据、是否按用例类型区分）

### 3.2 问题：如何避免假做 TDD

**描述**：LLM 可能生成"迎合代码"的假测试（测试只测代码已经做的事，而非应该做的事）。

**已有解决方案参考**：

| 方案 | 来源 | 核心做法 | 不足 |
|------|------|----------|------|
| 针对假 TDD 特殊处理 | Moai-adk | 专门检测和防止 LLM 生成迎合代码的假测试 | 仅依靠 LLM 保证质量，缺乏外部验证手段 |
| 评测集独立 | 飞轮方案 | 用于评测的知识/代码不得参与知识生成时的上下文 | 需要严格隔离机制 |
| 防作弊（防背源码） | 飞轮方案 | 评测用代码优先用私有代码，公开代码需做变换（改命名/结构调整） | 变换规则待定义 |
| 默认源码正确 | pptx Slide 17 | 是 code 错了还是 test 错了，依靠源码跑 test 确定，默认源码正确 | 源码本身有 bug 时会误判 |
| Test-First + Red Phase 确认 | Spec Kit (GitHub) Article III | 强制要求测试先于实现编写，且必须确认测试在实现前是 FAIL 的（Red phase），从流程上杜绝"测试迎合代码" | 依赖人工确认 Red phase，飞轮需自动化 |

**飞轮当前设计**：
- 评测集独立约束（门禁与评测机制.md §3.5）
- 防作弊约束（门禁与评测机制.md §3.5）

**与 Spec Kit 的关系**：Spec Kit 的 Red Phase 确认机制是防止假 TDD 的直接手段——如果测试在实现前就通过了，说明测试没有实际验证价值。飞轮可借鉴此机制：UT 生成后先在源码上运行确认覆盖预期路径，再用生成代码运行，对比两套结果差异。但飞轮的"默认源码正确"与 Spec Kit 的"人工确认 Red phase"需要找到自动化结合点。

**待解决的问题**：
- 假 TDD 检测的具体实现机制
- 当源码本身存在 bug 时如何处理

### 3.3 问题：如何判断是 code 的问题还是 test 的问题（信用分配）

**描述**：测试失败时，难以判断是生成的代码有问题，还是测试用例本身有问题。

**已有解决方案参考**：

| 方案 | 来源 | 核心做法 | 不足 |
|------|------|----------|------|
| 双轨精炼 | TDD-Agent (2026) | 同时维护代码和测试两条轨道，在迭代中共同精炼 | 信用分配缺乏形式化方法 |
| 默认源码正确 | pptx Slide 17 | 依靠源码跑 test 确定，默认源码正确 | 源码有 bug 时失效 |
| In-Execution debug | Revisit Self-Debugging (2025) | 从运行时中间状态获取反馈，用 debug 确定 test 正确性 | 信息噪声大，实现难度大 |
| 错误跟进修复（假设源码正确） | CoverUp (FSE 2025) | 测试执行失败时，将错误信息回传 LLM，要求"修改测试以修正错误"，默认源码正确、测试有 bug | 源码本身有 bug 时会错误修复测试以迎合源码 |

**飞轮当前设计**：默认源码正确，依靠源码跑 test 确定问题方（pptx Slide 17）。

**与 CoverUp 的关系**：CoverUp 的错误跟进机制与飞轮的"默认源码正确"假设完全一致——测试失败时默认是测试的问题，将错误信息回传 LLM 修复测试而非修代码。CoverUp 的实践证明了此策略在覆盖率导向场景中可行（89% 行覆盖率），但飞轮的信用分配问题更复杂：飞轮中测试失败可能是知识文档不完整导致 Coder 生成了错误代码，而非测试本身有问题。CoverUp 的场景更简单（源码固定，只改测试），飞轮需要区分"测试有 bug"和"知识不完整导致代码有 bug"两种情况。

**待解决的问题**：
- 信用分配缺乏形式化方法（TDD-Agent 缺点）
- 源码自身有 bug 时的回退策略
源码和test正确性判定

### 3.4 问题：门禁评测的可靠性

**描述**：门禁是飞轮的"裁判"，裁判不可靠则飞轮方向不可靠。自进化 Agent 存在同配置重复实验方差巨大、任务顺序影响结果、目标规格模糊导致改进跑偏等问题。

**已有解决方案参考**：

| 方案 | 来源 | 核心做法 |
|------|------|----------|
| 重复评测 ≥ 5 次 | 飞轮方案（依据：Fragility of Self-Improving Agents） | 任何"知识优化后效果提升"的结论必须多次重复门禁评测，报告均值 ± 方差 |
| 控制任务顺序 | 飞轮方案 | 知识生成/优化的执行顺序是影响质量的变量，对比实验必须固定顺序 |
| 精确定义目标 | 飞轮方案 | 门禁阈值必须定义到可执行级别：相似度怎么算、对齐粒度、允许什么差异 |
| 客观信号优先 | 飞轮方案 | 反馈信号来自客观对比（生成代码 vs 源码、编译检查、测试结果），不依赖 LLM 自我评估 |
| 多信号组合 | 飞轮方案 | 门禁 = 源码对比（结构）+ 编译检查（环境）+ 测试（结果），单一指标会误判 |
| Converge 收敛检查 | Spec Kit (GitHub) `/speckit.converge` | 评估代码库与 spec/plan/tasks 的对齐程度，将未完成的工作追加为新 tasks，循环 implement → converge 直到 Converged | 对齐检查依赖 LLM 判断，非客观信号；面向 spec 而非知识文档 |
| 测试隔离 + Flaky 检测 | CoverUp (FSE 2025) | 隔离执行每个测试避免状态污染；用 `pytest-repeat` 多次运行检测 flaky test；三种隔离策略（隔离执行/禁用污染测试/禁用失败测试） | 仅 Python/pytest；隔离执行开销大 |
| 覆盖率停滞检测 + LLM 逃逸 | CODAMOSA (ICSE 2023) | 检测 SBST 覆盖率停滞（stallLen > maxStallLen 时触发），按覆盖率反比采样低覆盖函数，用 LLM（Codex）生成示例测试注入种群重启搜索；back-off 机制：LLM 注入无效时 maxStallLen 倍增避免浪费 LLM 调用 | 面向 SBST 搜索场景，飞轮门禁非搜索场景；但停滞检测 + 触发外部干预的反馈模式可参考 |

**飞轮当前设计**：知识飞轮流程设计.md §9 已定义五条硬性约束（重复验证、控制顺序、精确定义目标、客观信号优先、防知识污染）。

**与 Spec Kit 的关系**：Spec Kit 的 `/speckit.converge` 提供了"代码库 ↔ 规格对齐度评估 + 差距转任务"的闭环机制，与飞轮的"门禁评测 → 反馈 → 修改知识"闭环结构对应。飞轮可借鉴 converge 的"将差距转化为具体待办"思路——门禁不通过时，自动将差异项转化为知识修订任务。但飞轮的门禁需要客观信号（编译、测试、AST 对比），Spec Kit 的 converge 依赖 LLM 判断。

**与 CoverUp 的关系**：CoverUp 的测试隔离和 flaky test 检测机制直接解决飞轮门禁评测的可靠性问题——如果门禁评测本身不稳定（flaky test 导致通过率波动），飞轮的反馈就是不可靠的。CoverUp 用 `pytest-repeat` 多次运行检测 flaky test 的做法可直接采用。CoverUp 的三种隔离策略（隔离执行/禁用污染测试/禁用失败测试）也可参考用于飞轮门禁的测试执行环境设计。

**与 CODAMOSA 的关系**：CODAMOSA 的覆盖率停滞检测机制提供了一种"门禁信号何时该触发外部干预"的量化思路——不是每轮都调用 LLM，而是在连续 maxStallLen 轮覆盖率无提升时才触发 LLM 注入，并配合 back-off 机制（LLM 注入无效时 maxStallLen 倍增）。飞轮门禁可借鉴此模式：当门禁分数连续多轮无改善时，触发更激进的知识修订策略（如重写而非微调），而非每轮都用相同策略反复尝试。CODAMOSA 的 back-off 机制也可参考——如果激进修订后门禁分数仍无改善，应增大触发阈值避免浪费 LLM 调用。

**待解决的问题**：
- 80% 相似度的具体计算口径未定义（门禁与评测机制.md §4）
- 对比粒度（模块/文件/函数级）未确定
- 置信度计算公式未确定

## 第四阶段：反馈迭代

### 4.1 问题：如何修改生成知识库的 skill

**描述**：飞轮迭代中，不仅知识文档需要修改，生成知识库的 skill 本身是否也需要迭代更新？

**已有方案探讨**（pptx Slide 24）：

| 策略 | 做法 | 风险 |
|------|------|------|
| skill 包含迭代描述 | skill 本身包含迭代的描述，直接依靠 skill 的迭代部分 | skill 会越来越臃肿 |
| 独立 skill 修改 | skill 只负责生成知识库，由主 agent 用另一个 skill 修改 | 主 agent 自由修改过于不可控、不稳定 |
| 不修改 | 通用问题应修改，个别问题加入特征触发机制 | 无法通过门禁时缺乏应对 |
| 记录后修改 | 不当场修改而是先记录，后续通过记录频率来确定是否修改 | 响应慢，但更可控 |
| Constitutional Amendment | Spec Kit (GitHub) | 宪法条款不可变但可修正：修改需明确记录理由、维护者审批、向后兼容性评估，修正案带日期记录演化历史 | 面向架构原则，非面向生成 skill |

**核心约束**：skill 的更新需要严格把控，避免特例或错误信息被纳入，因为本身迭代就是一种容错机制（pptx Slide 3）。

**与 Spec Kit 的关系**：Spec Kit 的 Constitutional Amendment 机制（修改需记录理由 + 审批 + 向后兼容性评估 + 日期追踪）可直接参考用于飞轮 skill 的更新管控——skill 修改时需记录修改理由、评估对已有知识的影响、追溯修改历史。这对应飞轮"记录后修改"策略的可控版本。

**待解决的问题**：
- 是否需要修改 skill，还是只修改知识文档
- 如果修改，如何保证修改的准确性和必要性
- 如何避免 skill 在多轮迭代后臃肿影响模型判断

### 4.2 问题：如何修改知识库

**描述**：反馈迭代的依据包括代码 diff、门禁反馈（用例通过率、AST 相似度、模型反馈），如何根据这些信息修改知识库？

**已有解决方案参考**：

| 方案 | 来源 | 核心做法 |
|------|------|----------|
| 溯源链接反向映射 | 飞轮方案 | diff 差异 → 定位差异最大的源码位置 → 通过溯源链接反向找到知识文档对应段落 → 只改这一段 |
| 遵循依赖关系修改 | pptx Slide 25 | 将链上所有知识以及目录修改 |
| 结构化信号 + 自然语言解读 | 飞轮方案 | 两层反馈：结构化信号（diff 定位、相似度分数）+ 自然语言解读（差异原因 + 建议改哪部分） |
| 按代码单元迭代 | 飞轮方案 | 按函数/模块级迭代，不整篇文档迭代，每个单元独立评估、独立过门禁、独立合并 |
| 归因修订 | wpKnowledge MVP 迭代方向 | 按 sources 反向映射薄弱点到段落，让修订 agent 只改被点名的段落 |
| Converge → 差距转任务 | Spec Kit (GitHub) `/speckit.converge` | 评估代码库与 spec/plan/tasks 对齐度，将未完成/不符合的部分追加为新 tasks，循环 implement → converge 直到收敛 | 差距识别依赖 LLM，非客观对比；面向 spec 而非知识文档 |
| 覆盖率反馈循环 | CoverUp (FSE 2025) | 覆盖率分析 → 精确定位未覆盖行/分支 → 反馈给 LLM 要求修改 → 重新执行 → 重复直到收敛；客观信号（行号/分支号）驱动迭代 | 面向测试覆盖率而非知识质量；迭代目标单一（覆盖率） |
| 停滞信号触发 + back-off | CODAMOSA (ICSE 2023) | 覆盖率停滞（连续 maxStallLen 轮无提升）作为触发信号 → LLM 生成测试注入种群 → 若注入无效则 maxStallLen 倍增（back-off）避免浪费；low-coverage targeting 按覆盖率反比概率优先处理最薄弱函数 | 面向 SBST 搜索场景；但"停滞→触发→back-off"的反馈模式可泛化 |

**飞轮当前设计**：
- 知识文档每段标注 sources（文件:行 / 函数 / 模块），OKF frontmatter 中 `sources` 字段（知识飞轮流程设计.md §4）
- 知识薄弱点地图：某段知识反复触发差异 → 标记为薄弱段落优先重写（知识飞轮流程设计.md §4.3）

**与 Spec Kit 的关系**：Spec Kit 的 `/speckit.converge` 的"差距转任务"闭环与飞轮的"门禁反馈 → 知识修订"闭环结构一致。飞轮可借鉴 converge 的"将差异项转化为具体修订任务"机制——门禁不通过时，自动将差异最大的知识段落标记为待修订项，生成修订任务清单。但飞轮需要基于客观信号（diff 定位、相似度分数）而非 LLM 判断。

**与 CoverUp 的关系**：CoverUp 的覆盖率反馈循环与飞轮的"diff 反馈 → 知识修订"循环结构高度一致——两者都是"客观信号精确定位问题 → 反馈给 LLM 修改 → 重新评估 → 重复直到收敛"。CoverUp 的经验证明了这种客观信号驱动的迭代收敛是可行的（80% 中位覆盖率）。飞轮可借鉴 CoverUp 的具体做法：(1) 反馈信息要精确到行/分支级别（飞轮对应：精确到知识文档段落级别）；(2) 每轮只要求修改未覆盖部分而非重写全部（飞轮对应：只改被点名的薄弱段落）；(3) 设置迭代上限避免无限循环。

**与 CODAMOSA 的关系**：CODAMOSA 提供了 CoverUp 未覆盖的两种反馈迭代策略：(1) **停滞检测 + back-off**——不是每轮都触发 LLM 修订，而是在连续多轮无改善时才触发，且触发无效时自动增大阈值（maxStallLen 倍增），避免在无法改善的盲点上浪费 LLM 调用。飞轮可借鉴此模式：当某段知识反复修订后门禁分数仍无改善，自动增大该段落的再次修订阈值（标记为"顽固薄弱点"），转而尝试其他段落或升级修订策略（从微调改为重写）。(2) **按薄弱程度优先排序**——CODAMOSA 按覆盖率反比概率采样目标函数，覆盖率最低的函数被优先处理。飞轮可借鉴此策略：在多段落同时待修订时，按门禁分数差距排序，优先修订差距最大的知识段落，而非平均用力。

**待解决的问题**：
- 薄弱点地图的量化定义（触发几次算薄弱）
- 迭代轮次上限 / 成本控制
- 知识生成的粒度与切分策略（上亿行代码如何切片）

### 4.3 问题：测试可信度是飞轮闭环的前提

**描述**：现实代码生成场景中 oracle test（标准答案测试）通常不可用。如果测试本身不可信，飞轮的反馈就是错的。

**已有解决方案参考**：

| 方案 | 来源 | 核心做法 | 不足 |
|------|------|----------|------|
| In-Execution 思路 | Revisit Self-Debugging (2025) | 从运行时中间状态获取反馈而非仅依赖最终输出，用 debug 确定 test 正确性 | 存在信息噪声，实现难度大 |
| 源码跑 test 确定 | pptx Slide 17 | 依靠源码跑 test 确定测试可信度，默认源码正确 | 源码有 bug 时失效 |
| 重复评测 | 飞轮方案 | 重复评测 ≥ 5 次报告均值 ± 方差 | 成本高 |
| 覆盖率作为客观可信度信号 | CoverUp (FSE 2025) | 用行+分支覆盖率作为测试可信度的客观度量——覆盖率低说明测试未充分执行代码路径；配合 flaky test 检测排除不稳定测试 | 高覆盖率 ≠ 行为正确，仅证明执行了代码路径 |
| 覆盖率作为搜索 fitness 信号 | CODAMOSA (ICSE 2023) | 用覆盖率作为 SBST 进化算法的 fitness 函数，量化评估测试质量：每个函数 0-1 覆盖率评分，按评分驱动搜索方向（低覆盖函数优先）和停滞检测 | 覆盖率仅衡量执行路径，不衡量 oracle 正确性；CODAMOSA 明确不生成 test oracle |

**待解决的问题**：
- 如何在不依赖 oracle test 的前提下保证测试可信度
- 运行时中间状态信息量大，如何提取有用信号并避免噪声

**与 CoverUp 的关系**：CoverUp 用覆盖率作为测试质量的客观度量——如果测试连代码路径都没走完，可信度必然不足。这为飞轮提供了一个可量化的测试可信度下限：UT 覆盖率低于某阈值时直接判定测试不可信，不进入门禁评测。CoverUp 的 flaky test 检测（`pytest-repeat` 多次运行）也可直接用于飞轮——flaky test 不能作为门禁信号，需检测并排除。

**与 CODAMOSA 的关系**：CODAMOSA 将覆盖率从"度量指标"提升为"搜索 fitness 函数"——覆盖率不仅用于评估测试好坏，还直接驱动测试生成的方向（低覆盖函数优先）和节奏（停滞检测触发 LLM 注入）。CODAMOSA 的 per-function 覆盖率评分（0-1）可为飞轮提供更细粒度的测试可信度分析：不是整体覆盖率达标即可，而是每个函数都需达到覆盖率下限。CODAMOSA 明确不生成 test oracle 的局限也提醒飞轮：覆盖率仅证明"执行了路径"，还需独立验证"路径行为正确"（飞轮的源码跑 test 确认机制覆盖此缺口）。

### 4.4 问题：防知识污染与回滚

**描述**：早期低质量知识可能被飞轮"学"进知识库（经验污染风险），优化可能使知识倒退。

**已有解决方案参考**：

| 方案 | 来源 | 核心做法 |
|------|------|----------|
| 版本控制 + 门禁 | 飞轮方案 | 知识变更走版本控制，未通过门禁的优化不得合并 |
| 自动回滚 | 飞轮方案 | 优化使知识倒退时（门禁分数下降），自动回退到上一版本 |
| 历史版本保护 | wpKnowledge MVP | 旧版本写入 `history/`，新版本评分失败时旧 verified 卡保留 |
| 草稿/正式分离 | wpKnowledge MVP | 未过门禁进 `drafts/`，过门禁进 `concepts/`，外部检索默认只搜 `concepts/` |

**飞轮当前设计**：知识飞轮流程设计.md §9.5 + FLYWHEEL-DESIGN.md §10.4/§10.5 已实现。

**待解决的问题**：
- 文件写入没有事务/锁（FLYWHEEL-DESIGN.md §11）
- 知识库是攻击面，来源可信性需管控

## 第五阶段：内外知识关联

### 5.1 问题：外部知识时效性

**描述**：外部文档会随版本更新过时，不可能直接遍历验证全量文档。

**已有解决方案参考**：

| 方案 | 来源 | 核心做法 | 不足 |
|------|------|----------|------|
| 时间有效性标注 + 废止链 | Temporal Validity in RAG (2025) | {valid_from, valid_until, superseded_by}，检索时自动过滤已废止条目 | 验证机制仅依靠 LLM 判断 |
| 双层图 + 时间边 | RAG Meets Temporal Graphs (2025) | 知识图谱关系边附加时间信息 | 未在代码场景验证 |
| 半衰期公式 | Solving Freshness in RAG (2025) | 量化计算知识有效期限 | 仅以时间为维度，过于简化 |
| 验证时间 snapshot | pptx Slide 31 | hash 不变→继承结论；hash 变了→标记重验变更部分；内部版本变了→关联关系待确认 | 需要维护 hash 指纹体系 |
| 分级处理 | pptx Slide 32 | verified / stale / invalid / revalidating 四状态分级 | 状态转换逻辑待细化 |

**飞轮当前设计**：
- pptx 提出验证结论状态分级：verified（上下文指纹全匹配）/ stale（有漂移但未重验）/ invalid（重验失败）/ revalidating（重验中）
- wpKnowledge MVP 已实现 `stale_after` 时效衰减信号

**待解决的问题**：
- 自动化环境搭建困难，工具无法包含在文档验证中
- 文档数量庞大，实时更新及未知因素（版本更新导致已验证文档过时）难以全量处理

---

### 5.2 问题：如何关联内外知识

**描述**：外部知识如何与内部代码知识库建立关联？

**已有方案探讨**（pptx Slide 29）：

| 方案 | 做法 |
|------|------|
| 由外到内 | 外部知识提到的内部相关代码部分进行双向关联 |
| 由内到外 | 消费知识库过程中遇到问题无法单纯依靠知识库解决时，查找外部知识文档，验证后双向关联 |
| 用时验证 | 工具集管理的自动化扩展 + 权限控制，用时验证记录上次验证成功经验 |
| 缺口检测 | 某个知识经常在消费中被需要但内外都查不到时，标记知识缺口 |
| 外部知识自身关联 | 外部知识文档之间存在关联关系 |

**扩展策略**（pptx Slide 33）：
1. 锚点选择：找内部知识库里引用最多、问题最多领域的外部文档作为首批验证对象
2. 辐射扩展：锚点文档验证后，沿其关联链逐步扩展
3. 按需扩展：内部消费遇到问题时搜索到的外部文档，验证后纳入

**置信度分级**（pptx Slide 33）：
- Agent 实际依赖的外部知识验证到 L2
- 引用到的到 L1
- 只存在的到 L0

**待解决的问题**：
- 只有已验证的外部知识才进行关联
- 外部知识完整性（关联到模型能否有足够知识去实现）
- 外部知识本身可能存在省略、残缺

---

### 5.3 问题：最需要关联何种信息（隐性知识缺失）

**描述**：AI 编码助手在企业级长周期复杂系统中频繁失败，根因是隐性知识缺失（设计理由、历史决策、跨团队依赖等未编码在源码中）。

**已有解决方案参考**：

| 方案 | 来源 | 核心做法 | 不足 |
|------|------|----------|------|
| 代码伴生知识库 | Code Digital Twin (2026) | Code & Artifact Map（物理层结构化导航）+ Functionality-oriented Skeleton（概念层骨架），将设计决策、历史背景等隐性知识结构化存储 | 实现难度大 |
| OKF 知识卡 | wpKnowledge | Markdown + YAML frontmatter，sources 溯源 + status 状态 + verified 信任级别 | 隐性知识提取自动化程度不足 |

**飞轮当前设计**：
- 知识形态定义为"伪代码 + 为什么这样设计 + 解决什么问题 + 适用场景"（知识形态定义.md），本身就是对隐性知识的编码
- OKF 知识卡模板包含 `## 概述`（为什么有这个东西）、`## 适用场景`（什么时候用）等字段

**待解决的问题**：
- 隐性知识的提取、结构化、与代码同步更新都面临较大挑战
- 设计理由、历史决策等信息通常记录在工单/邮件中而非代码中

---

### 5.4 问题：外部文档的修补

**描述**：外部文档过时导致验证失败时，如何修补？

**已有方案探讨**（pptx Slide 34）：
- 允许模型介入修改过时的外部文档
- 修补流程可直接复用飞轮框架，将门禁改成对文档的验证
- 修补时需提供材料（参考代码 diff、验证反馈等）

**待解决的问题**：
- 外部文档的修改权限和审核机制
- 修补后的文档如何重新验证并纳入知识库

---

### 5.5 问题：外部知识索引组织

**描述**：外部知识数量庞大，如何组织索引？

**已有方案探讨**（pptx Slide 36）：
- 采用 OKF 形式，依靠不断引入新知识自涌现目录结构
- 先判断是否能归入已有目录结构中，不能则新建
- 文档过多时生成子目录

**飞轮当前设计**：
- wpKnowledge MVP 已实现 `store/index.md` 渐进式披露索引（自动生成）
- OKF Bundle 按目录树自包含组织

**待解决的问题**：
- 自涌现目录结构的算法实现
- 文档过多时子目录生成的触发条件

## 普遍存在的不足（跨阶段总结）

| 不足 | 影响阶段 | 现状 |
|------|----------|------|
| **知识验证缺乏** | 知识生成 | 多数方案"生成即完成"，飞轮通过代码还原验证但尚未完整实现 |
| **知识无时间维度** | 知识生成、内外关联 | 增量更新机制不完善，wpKnowledge MVP 有 `stale_after` 但语义一致性验证未实现 |
| **验证依赖 LLM 判断** | 评测门禁 | 有验证机制的方案也基本依赖 LLM 自身判断，缺乏可执行/可量化的验证手段。OpenSpec 的 `/opsx:verify` 和 Spec Kit 的 `/speckit.analyze` + `/speckit.converge` 均依赖 LLM 判断，飞轮需用客观信号（编译、测试、AST 对比）补充。CoverUp 和 CODAMOSA 用覆盖率作为客观信号，但覆盖率仅证明执行了路径，不验证行为正确性 |
| **缺少形式化方法** | 评测门禁、反馈迭代 | 信用分配（代码 vs 测试的归因）、知识可信度评估等环节缺乏形式化方法 |
| **文件写入无事务/锁** | 反馈迭代 | wpKnowledge MVP 的并发安全性未保障 |
| **上亿行代码切分策略** | 知识生成、代码生成 | 知识生成的粒度与切分策略未定义 |
